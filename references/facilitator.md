# Facilitator ledger and recovery

Requires Python 3.9+ and no packages. The helper schedules and records work; it does
not call models, browse, select roles semantically, or enforce runtime token caps.
Only the facilitator runs it. Specialists write their assigned artifacts. Run paths
and script paths below are examples; resolve them absolutely when assigning work.

## Initialize

Prepare a brief and a JSON roster outside the new run directory. The roster is an
array with exactly the mode's seat count, sequential IDs, distinct concrete roles,
and a nonempty reason and remit for each. Example single entry (not a full roster):

```json
{"id":"S01","role":"Security Architect","reason":"Trust boundary is the core risk","remit":"Threat model and abuse resistance"}
```

```bash
python3 /path/to/fix-my-idea/scripts/facilitator.py .fix-my-idea/run-id init \
  --mode standard --budget 25000 --brief /tmp/brief.md --roster /tmp/roster.json
```

The helper copies BRIEF and generates ROSTER. Do not initialize over an existing
run. `--reserve` optionally overrides the default 20% synthesis reserve; it must
be positive and below budget. All modes allow budget overrides. Choose enough
reserve to read working records and produce the report, not only to emit its text.
Charge initial brief/roster preparation and instruction-loading estimates with
`charge` after initialization so setup is included in the target.

## Task loop

```bash
python3 /path/to/fix-my-idea/scripts/facilitator.py RUN resume
python3 /path/to/fix-my-idea/scripts/facilitator.py RUN start --input-tokens 900 --output-tokens 700
# Read STATUS for the authorized task; perform it and write its assigned output.
# Inspect format, substantive coverage, and evidence before marking complete.
python3 /path/to/fix-my-idea/scripts/facilitator.py RUN finish --tokens 1700 --basis 'text estimate'
```

Each command returns a compact JSON summary with the next task, assigned output,
character cap, remaining estimate and latest event. Read STATUS on disk only when
needed; `resume --verbose` prints it. Use `resume` on continuation or recovery,
not redundantly after every successful completion. `start` reserves the
estimated input plus output cost BEFORE work. Estimate all loaded instructions,
brief, research, repeated context, tool results and expected output, not only the
saved artifact. Fallback heuristic: ceil(UTF-8 bytes / 4). It is approximate,
especially for code and non-English text, and cannot see hidden reasoning or
unreported runtime overhead. Use runtime usage metadata only if available with a
known scope; supply a per-task total, never a cumulative session count repeatedly.
`finish --tokens` records that observation; the ledger conservatively retains a
higher reservation. STATUS totals are therefore estimates/mixed conservative
accounting, never exact billed tokens. Usage rows describe reservations and updates;
do not sum those rows to obtain a total. Use state.used.

If metadata is absent, estimate actual input + output including tool text and pass
that total. Without `--tokens`, the helper retains the reservation and checks saved
output size; this cannot account for unreported tool/context usage. `charge` adds
otherwise-unaccounted facilitator/tool work and records the reason. Avoid counting
the same usage twice. Record model/context limitations in BRIEF.

```bash
python3 /path/to/fix-my-idea/scripts/facilitator.py RUN charge --tokens 500 --reason 'Setup context estimate'
python3 /path/to/fix-my-idea/scripts/facilitator.py RUN fail --reason 'Missing risk-to-repair links' --tokens 1200
python3 /path/to/fix-my-idea/scripts/facilitator.py RUN skip --reason 'No material disagreement'
python3 /path/to/fix-my-idea/scripts/facilitator.py RUN stop --reason 'Evidence unavailable; prepare partial report'
```

`fail` permits at most one retry. `skip` only skips the next optional task. Skip
all remaining cycle-two tasks individually when not warranted, explaining why.
`stop` skips pending work except final synthesis; finish/fail running work first.
When admission would consume the reserve, `start` automatically records a stop and
moves to final synthesis. Read its result: a rejected specialist reservation is
NOT authorization to perform it. A final task may exceed the estimate to preserve
a useful report; the helper cannot impose a hard runtime limit. Disclose overruns.
If a runtime does enforce a hard cap, start synthesis earlier within that cap.

## Checkpoints and resume

`state.json` is authoritative, with a previous valid `state.backup.json`.
Writes use same-directory temporary files, flush/fsync, and atomic replacement.
`STATUS.md` is a derived view regenerated by `resume`; a crash between writes
cannot make STATUS authoritative. This is a single-writer design, not a concurrent
database or a guarantee against storage-device failure.

1. Use the existing run path. Load and validate state/schema/schedule; fall back to
   the previous valid checkpoint if current JSON is corrupt, recording recovery.
2. Verify hashes of completed artifacts and inputs. Review their substantive
   content too. Never run already completed specialists just to regenerate context.
3. A running task means interrupted/unknown outcome, not permission to restart it.
   Inspect its output and any live worker. If valid, finish it without another call.
   Otherwise stop the worker if possible, fail the attempt, then retry at most once.
   Its original reservation remains charged because consumption is uncertain.
4. A missing or altered completed artifact blocks new work. Restore the exact
   original from retained worker output or backup, then resume. If unavailable,
   stop and synthesize a partial report explicitly excluding invalid evidence.
   Do not trust or silently rerun downstream evaluations. An explicit user request
   may authorize a new linked run; preserve the original records and gap explanation.
5. If both checkpoints are invalid, stop automatic execution. Reconstruct state
   manually from validated artifacts and logs, preserving corrupt files for review;
   never call init over the old run. Do not invent usage or completion records.

Artifacts written after a recovered checkpoint may be unregistered: inspect and
adopt them via the normal start/finish sequence without invoking a specialist again,
recording the recovery decision and conservatively charging uncertain usage.
Do not overwrite such artifacts before inspection. A final synthesis failure also
has only one retry; report the location of completed work and the error if both fail.

## Manual fallback and v1

Without Python, maintain the same fields in STATUS and use atomic write/rename
when filesystem tools support it. Record mode, phase, roster completed/pending,
research/debates, attempts, estimated usage/reservations, generated paths, errors,
and next action. Explicitly disclose that machine validation is unavailable.
Without filesystem access, deliver labeled records in the conversation and say
nothing was saved; robust disk resume is unavailable.

For a v1 run without JSON, inspect STATUS and every existing artifact, retain its
12-seat scope as DEEP unless the user changes it, and continue with the manual
ledger. Never invent machine checkpoints or restart completed seats. New runs use
v2 defaults. Do not edit the user's installed skill while working on this repository.
